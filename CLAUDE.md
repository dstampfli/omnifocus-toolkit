# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Three OmniFocus automation utilities, a local MCP server that exposes them to Claude Desktop, two Omni Automation plug-ins (one of them targeting OmniOutliner, not OmniFocus), plus their shared scaffolding:

- `omnifocus_inbox_triage.py` reads every *open* OmniFocus Inbox task and uses the Claude API to classify each one against the user's existing active projects, moving high-confidence matches into their project. Each item's note and any PDF/image attachments are sent to a vision-capable model as part of classification; when `X_BEARER_TOKEN` is set, the text of any linked X (Twitter) post is fetched via the X API and included too.
- `omnifocus_task_reviewer.py` reviews not-yet-reviewed tasks in named OmniFocus project(s), enriching each in place — fetching any linked page via the model's web_fetch (and, when `X_BEARER_TOKEN` is set, the text of any linked X post via the X API) and reading its attachments to produce a clearer title and an appended, timestamped note summary — then marks it done with a **top-level** tag (`REVIEW_TAG`, default `Reviewed`, kept outside the Kanban lanes so reviewed items never land on the board) so re-runs skip it. The per-task reviews (each a slow blocking API call) run concurrently, up to `REVIEW_MAX_WORKERS` (default 5) at a time. Reuses `omnifocus_common`'s helpers.
- `omnifocus_sorter.py` reorders the **top-level tasks** of named OmniFocus project(s) by any of the eight keys OmniFocus sorts by natively (`title`, `status`, `added`, `completed`, `due`, `planned`, `defer`, `dropped`) or by a caller-supplied **tag priority order** (`--by tag` with repeated `--tag`, or the `tag_order` argument): each task sorts by the position of its highest-priority tag, matched case-insensitively by leaf name. Makes **no Claude API call** — two `osascript` round-trips regardless of project size. Dry-run by default; `--apply` writes.
- `omnifocus_kanban_board.py` serves a local drag-and-drop **Kanban board** (`http://127.0.0.1:8765/`, stdlib `http.server`, loopback only) over the `KANBAN_TAG` parent's child tags: each lane tag is a column and every open task carrying a lane tag is a card. Dropping a card re-tags the task exactly like the plug-in (`removeTags(all lanes)` + `addTag(lane)`). **No `--apply`** — each drop writes immediately — and **no Claude API call**. The page is `kanban_board/index.html` (vanilla HTML/CSS/JS, no external resources; its favicon is an inline SVG data URI in the head, so bookmarks get a board glyph without a separate file or route).
- `omnifocus_mcp_server.py` is a local **stdio** MCP server (FastMCP / `mcp[cli]`) exposing five tools — `triage_inbox`, `review_tasks`, `sort_project`, and the read-only `omnifocus_status` and `list_projects` — to a scheduled Claude Cowork task in Claude Desktop. It reuses the toolkit modules directly: `triage_inbox`/`review_tasks` call `run_triage`/`run_review`, `sort_project` calls `run_sort`, and `omnifocus_status`/`list_projects` call `read_omnifocus` — `omnifocus_status` returns just the open-Inbox/active-project counts, while `list_projects` returns each active project's id, name, folderPath, and description so a scheduled agent can discover project names dynamically (e.g. to fan a `review_tasks` call out over every active project). `review_tasks` reviews at most `max_tasks` tasks per call (default `DEFAULT_MAX_TASKS` = 5) and returns `remaining` = unreviewed tasks left, so the agent loops until `remaining` is 0 rather than making one unbounded call that can outlast the client's tool timeout. `apply` defaults false; each tool wraps failures into `{"error": ...}`. No network/auth/tunnel — Claude Desktop launches it locally over stdio.
- `omnifocus_common.py` holds task-enrichment helpers (`clean_note`, `media_type_for`, `attachment_block`, `extract_webloc_url`, `build_task_content`, `run_jxa`, `run_jxa_or_raise`/`JxaError`, `fetch_attachment_b64`, `_positive_int_env`) shared by the triage and reviewer scripts. `build_task_content` turns a `.webloc` attachment into a "Linked web page(s)" text line (URL parsed by `extract_webloc_url`) rather than a vision block, so the model can fetch the link.

- `omnifocus_kanban_plugin/of-kanban-board.omnifocusjs` is a vendored copy of the Omni Automation "Kanban Board" plug-in (v1.3), functionally identical to upstream's `To Do / In Progress / Waiting / Done`. A `Reviewed` lane was added in v1.2 and removed again in v1.3 when the task reviewer moved its tag to the top level; the copy is kept so the installed plug-in can be refreshed — its Display Board action recreates every lane in its list, so a stale 1.2 install would resurrect an empty `Kanban ▸ Reviewed` lane. See `omnifocus_kanban_plugin/README.md`.
- `omnifocus_automation/strikethrough.omnijs` is a standalone Omni Automation action plug-in (v1.2) targeting **OmniOutliner 6 Pro** (`"targets": ["omnioutliner"]` — the only non-OmniFocus code in the repo), run from the app's Automation menu (wired to `⌃⇧X` via Keyboard Maestro). It exists because OmniOutliner **Pro** has no Strikethrough menu command at all — Essentials does, so its docs mislead here, and the alternatives (the Style inspector's "S" button, a Unicode U+0336 overlay, a Named Style on `Control`+number) are all clickable-target or positional hacks. The action toggles `Style.Attribute.StrikethroughStyle` over each style in `selection.styles`, so a multi-row selection toggles each row *independently* (a mixed selection won't normalize); `action.validate` returns false on an empty selection, which greys out the menu item. Two API traps make it fragile to edit: (1) the enum class is `UnderlineStyle`, **not** `Underline.Style` — strikethrough attributes reuse the underline enums (`StrikethroughStyle`/`StrikethroughAffinity`/`StrikethroughPattern` take `UnderlineStyle`/`UnderlineAffinity`/`UnderlinePattern`), and referencing `Underline` throws `ReferenceError`; (2) **enum values are not singletons**, so `===` against `UnderlineStyle.None`/`.Single` is unreliable in both directions (two values can both print `None` yet compare false) and any toggle built on enum identity silently misbehaves — classically the first keypress appears to do nothing. Hence the toggle reads `style.localValueForAttribute(attr)`, which returns null/undefined when unset, instead of comparing enums, and clears with `style.set(attr, null)` rather than `UnderlineStyle.None` so inherited styling shows through instead of being pinned off. `get()` is the wrong method here: it cascades through inherited styles to the attribute default and so essentially never returns null, making "explicitly none" indistinguishable from "never set". Because the check reads only the *local* value, text inheriting strikethrough from a named style or theme reads as "not struck" — first press sets a visually no-op local strikethrough, second clears it (edge case only). Install via OmniOutliner's **Automation ▸ Configure…**, which surfaces load errors; the direct-download container path is `~/Library/Containers/com.omnigroup.OmniOutliner6/Data/Library/Application Support/Plug-Ins/` (the Mac App Store build differs). When an edit seems not to take effect, `grep` the *installed* file first to confirm it is the edited version — a stale cached copy produces an identical error message and sends you chasing the wrong thing; quit and relaunch OmniOutliner to clear it.

`main.py` is the unused `uv`-generated placeholder entry point.

## Commands

```bash
python3 omnifocus_inbox_triage.py            # dry-run: classify Inbox tasks and report, change nothing
python3 omnifocus_inbox_triage.py --apply    # classify, then move high-confidence matches into their project

uv sync                                      # install the anthropic/pydantic dependencies
uv run pytest                                # run the unit tests
```

`omnifocus_inbox_triage.py` follows a dry-run-by-default / `--apply`-to-write safety model: dry-run is the implicit default and `--apply` opts into writing.

```bash
python3 omnifocus_task_reviewer.py "Training"          # dry-run: show proposed enrichments
python3 omnifocus_task_reviewer.py "Training" "Tech"   # multiple projects
python3 omnifocus_task_reviewer.py "Training" --apply  # write: rename, append summary, tag reviewed
```

`omnifocus_task_reviewer.py` follows the same dry-run-by-default / `--apply`-to-write model as the triage tool.

```bash
python3 omnifocus_sorter.py "Training" --by due                  # dry-run: show the new order
python3 omnifocus_sorter.py "Training" "Tech" --by title         # multiple projects
python3 omnifocus_sorter.py "Training" --by added --desc --apply # write: newest first
```

`omnifocus_sorter.py` follows the same dry-run-by-default / `--apply`-to-write model.

```bash
python3 omnifocus_kanban_board.py [--port 8765] [--no-open]   # serve the Kanban board and open it
```

`omnifocus_kanban_board.py` has **no** dry-run mode: each drop on the board writes immediately.

## Architecture

Both tools embed a JXA (JavaScript for Automation) program run via `osascript -l JavaScript`, with a Python side that handles CLI flags and formats output; all cross-process communication is JSON strings over `osascript`'s argv/stdout.

`omnifocus_inbox_triage.py` inserts a Claude API classification stage between an OmniFocus read and an OmniFocus write, giving it three stages:

1. **Read** (`READ_JXA` / `read_omnifocus`): JXA pulls every *incomplete* Inbox task (completed tasks are skipped — `inboxTasks()` includes finished items) and every project (with id, name, folder path, status, and its OmniFocus note as `description`); the Python side filters to active projects.
2. **Classify** (`classify`): the items and projects are sent to the Claude API via `client.messages.parse(..., output_format=Classification)`, using structured output (Pydantic models `Decision`/`Classification`) so the model returns one typed decision per Inbox item instead of free text to parse. `build_user_message` sends an ordered list of content blocks — a leading text block with the slimmed project taxonomy (id, name, folderPath, `description`), then per item a text header plus a vision block per in-scope attachment (built via `omnifocus_common.build_task_content`). The project note is the primary signal for what belongs where, taking precedence over the project name. Attachment bytes are extracted via `omnifocus_common.fetch_attachment_b64`, which goes through OmniFocus's OmniJS `evaluateJavascript` bridge because plain JXA cannot read attachment contents; the default model is now `claude-sonnet-5`, which must be vision-capable to read them. Classification is batched: `classify_in_batches` splits items via the size-aware `batch_items_by_size` helper, which flushes a batch once it hits `CHUNK_SIZE` items *or* its in-scope attachment bytes would exceed `MAX_BATCH_ATTACHMENT_BYTES`, calls `classify` once per batch, and concatenates the resulting `decisions` lists — keeping each call's output and attachment payload under the model's limits. When `X_BEARER_TOKEN` is set, `build_user_message` also appends any linked X post's text to an item's header via `omnifocus_x` (a run-scoped `XPostFetcher` built in `classify_in_batches` dedupes by post id and caps lookups at `X_FETCH_MAX_USES`, default 25); the fetched text is model input only and never enters the OmniJS write source. With no token the step is skipped.
3. **Apply** (`WRITE_JXA` / `apply_moves`): for decisions that clear `MOVE_MIN_CONFIDENCE`, a second JXA program moves each task into its matched project — run only when `--apply` is passed. The move goes through OmniFocus's **Omni Automation (OmniJS) bridge** (`evaluateJavascript` + `moveTasks(task, project.ending)`), matching tasks/projects by identifier. Note: setting `assignedContainer` from JXA is *not* enough — it only marks a pending assignment and does not relocate the task (yet reports success), which is why the OmniJS bridge is used. Only whitelisted ids (already checked against the real OmniFocus id sets) are embedded into the OmniJS source string — never task names, notes, or other free text.

Config (`MODEL`, `MOVE_MIN_CONFIDENCE`, `CHUNK_SIZE`, plus the attachment/note caps `MAX_ATTACHMENT_BYTES`, `MAX_BATCH_ATTACHMENT_BYTES`, `MAX_NOTE_CHARS`) is read and validated at import by `_load_config()` — a bad `.env` value (non-numeric/non-positive `CHUNK_SIZE` or byte/char cap, an unrecognized `MOVE_MIN_CONFIDENCE`) exits with a clear message instead of a raw traceback, and `MOVE_MIN_CONFIDENCE` is case-normalized. `load_dotenv()` runs first so a gitignored `.env` can supply these plus `ANTHROPIC_API_KEY` (which the `anthropic` SDK reads from the environment directly — no code passes it). `.env.example` is the committed template. All cross-process communication is JSON over `osascript`'s argv/stdout. The pure decision/parsing/prompt-building/reporting logic (everything except the two JXA calls, `fetch_attachment_b64`, and the live API call) is unit-tested under `tests/` — this includes `batch_items_by_size`, but not `classify_in_batches`, which is thin I/O orchestration over the untested `classify`. `omnifocus_common.py`'s pure helpers (`clean_note`, `media_type_for`, `attachment_block`, `build_task_content`) are likewise unit-tested; `run_jxa` and `fetch_attachment_b64` are the I/O boundary and are not. Both `omnifocus_inbox_triage.py` and `omnifocus_task_reviewer.py` now factor their orchestration into a shared `_triage_pipeline` / `_review_pipeline` helper that both the CLI `main()` and a structured-result `run_triage` / `run_review` call — `run_*` returns a JSON-serializable dict consumed by `omnifocus_mcp_server.py`, while `format_report` (and its tests) are unchanged.

`omnifocus_task_reviewer.py` reuses the same embedded-JXA-over-`osascript` pattern for a three-stage pipeline scoped to named projects instead of the Inbox: **read** (`READ_TASKS_JXA`) walks each named project's tasks entirely in OmniJS — skipping completed, dropped, any task carrying a tag named `REVIEW_TAG` (the top-level review tag, matched by exact case-sensitive name), and any task already on the Kanban board (carrying **any** tag in the `KANBAN_TAG` subtree — the `Kanban` parent or any descendant lane, matched by tag identity — so a task pulled onto the board keeps being skipped as it progresses `To Do → In Progress → Done` even if its review tag is removed) — and returns each task's id, name, note, and attachment metadata; **review** (`review_task`) makes one `client.beta.messages.parse(..., output_format=Enrichment)` call per task with the `web_fetch` beta tool (capped at `WEB_FETCH_MAX_USES` uses) enabled, so the model can follow a URL in the note before producing a typed `Enrichment` (`new_title`, `summary`) — `review_tasks` runs these per-task calls concurrently via a `ThreadPoolExecutor` (up to `REVIEW_MAX_WORKERS`, default 5, capped at the task count) while preserving input order in its results, and catches failures per task so one bad task never aborts the run; **apply** (`WRITE_JXA` / `apply_enrichments`), run only under `--apply`, sets `name`/`note` **and** adds the tag in a single OmniJS `evaluateJavascript` call. The review tag (`REVIEW_TAG`, default `Reviewed`) is a **top-level tag, deliberately outside the `Kanban` parent**: reviewed items are a reading pile, not board work, so the board shows only tasks pulled onto it by hand. The apply stage resolves it with `tags.byName` (top-level only); if instead a legacy `Kanban ▸ Reviewed` lane exists it is moved to the top level with `moveTags([nested], tags.ending)` — which keeps every task's tag, so that one call is the whole migration — and otherwise the tag is created at the top level. It is never created under `Kanban`. (This reverses an earlier design that nested `Reviewed` as the board's first lane; that lane made the board 60% reading material.) OmniFocus tag lookup is **case-sensitive**, which is why the default is `Reviewed`, not `reviewed`. `KANBAN_TAG` is reviewer-specific config alongside `REVIEW_TAG` and `WEB_FETCH_MAX_USES`. The note must be set through OmniJS, not plain JXA: assigning `t.note` via the JXA/Apple-Events bridge replaces the note's rich text and destroys its embedded attachments (`.webloc` links, PDFs, images), whereas the OmniJS assignment preserves them. To keep the model's free text out of the OmniJS *source* (injection safety), each title/note is percent-encoded with `encodeURIComponent` in JXA — whose output cannot break out of a JS string literal — and decoded with `decodeURIComponent` inside OmniJS; only task ids, that encoded text, and the (trusted, config) tag names (`REVIEW_TAG` and `KANBAN_TAG`) reach the source. `MAX_ATTACHMENT_BYTES`/`MAX_NOTE_CHARS` are shared with the triage tool's config; `REVIEW_TAG`, `WEB_FETCH_MAX_USES`, and `REVIEW_MAX_WORKERS` are reviewer-specific, validated the same way (`_positive_int_env`, now defined in `omnifocus_common.py` and imported by both `omnifocus_inbox_triage.py` and `omnifocus_task_reviewer.py`). Both `omnifocus_inbox_triage.py` and `omnifocus_task_reviewer.py` now factor their orchestration into a shared `_triage_pipeline` / `_review_pipeline` helper that both the CLI `main()` and a structured-result `run_triage` / `run_review` call — `run_*` returns a JSON-serializable dict consumed by `omnifocus_mcp_server.py`, while `format_report` (and its tests) are unchanged. `_review_pipeline`/`run_review` take a `max_tasks` cap: when set, only the first `max_tasks` read tasks are reviewed this call and the result carries `remaining` = the count left unreviewed (the MCP `review_tasks` tool passes `DEFAULT_MAX_TASKS` = 5 and the scheduled agent loops until `remaining` is 0); the CLI passes no cap and reviews everything.

`omnifocus_sorter.py` reuses the embedded-JXA-over-`osascript` pattern for a three-stage pipeline, but with **no model stage**: **read** (`READ_SORT_TASKS_JXA` / `read_project_tasks`) walks each named project's **direct children** (`project.children`, *not* `flattenedTasks` — action-group subtasks keep their own order) in OmniJS and returns each task's id, name, status name, and the six date fields as **epoch milliseconds or null** (numeric comparison sidesteps timezone/format ambiguity); unresolvable project names are collected into `missing` rather than aborting. **sort** (`sort_tasks`, pure Python and unit-tested) orders tasks by one of the eight `SORT_KEYS` — tasks with no value for the key always sort **last in both directions** (nulls are split out before sorting, so `descending` can never float them to the top), and the sort is **stable**, so ties keep their input order and re-sorting is idempotent. `status` uses `STATUS_RANK`, an explicit **urgency-first** rank (`Overdue → DueSoon → Next → Available → Blocked → Completed → Dropped`) rather than the meaningless OmniJS `Task.Status.all` declaration order; an unrecognized status sorts after all known ones. An unknown sort key raises `SystemExit` with the valid keys, validated *before* any OmniFocus read. A ninth basis, `tag`, is not a `SORT_KEYS` member (it needs the caller's `tag_order` list) and is validated separately by `_validate_sort`: `by="tag"` with an empty/missing `tag_order` raises `SystemExit` before any OmniFocus read. Its sort value is the minimum `tag_order` index among a task's tags (earliest-listed tag wins), or null — so unmatched tasks fall into the same null bucket that always sorts last. The read stage returns each task's leaf tag names (`tags`) for this; only task/project identifiers still reach the write source, so tag sorting adds no new free text to escape. **apply** (`WRITE_SORT_JXA` / `apply_order`), run only under `--apply`, moves each task to `project.ending` in sorted order — appending in sequence leaves the project in exactly that order. Only project/task **identifiers**, whitelisted by `build_write_config` against the id set the read stage returned, reach the OmniJS source; there is no model free text to percent-encode (unlike the reviewer). `_sort_pipeline` skips the write entirely for a project whose order already matches, and `run_sort` reports per-project `changed` so a scheduled agent can see that. No new env config — `by`/`descending` are per-call arguments — and no per-call batching cap, since sorting makes no API calls and so has no tool-timeout pressure regardless of project size.

`omnifocus_kanban_board.py` reuses the embedded-JXA-over-`osascript` pattern behind a small HTTP API instead of a CLI pipeline. `BoardApp` holds the endpoint logic with no HTTP types (each method returns `(status, payload)`; `read`/`move` are injectable), and `KanbanHandler`/`make_server`/`serve` are thin plumbing. **Read** (`READ_BOARD_JXA` / `read_board`) resolves the `Kanban` parent by name, takes its `children` in OmniFocus order as the lanes, and emits every open task in each lane as a raw card (id, name, `lane_id`, project, due/defer/added as epoch ms, flagged, status name, non-lane tag names as `tags` and the same tags' ids as `tag_ids`, note capped at `MAX_NOTE_CHARS`) plus the **tag tree** — every tag outside the `KANBAN_TAG` subtree, in OmniFocus order with parents before children, dropped tags skipped, each as id/name/`parent_id`; a missing parent tag is reported as `missing_kanban_tag` and mapped to a `409` with guidance. `build_board` (pure, unit-tested) hides completed/dropped cards, keeps the first lane for a task carrying two lane tags, turns the note into a `note_excerpt` via `clean_note`, and sorts with `sort_cards` (keys `due`/`title`/`project`/`added`, nulls always last, stable — the page re-sorts client-side). It also expands each card's `tag_ids` to include every ancestor (`expand_tag_ids`; OmniFocus only ever reports the directly assigned tags) and emits `tags` via `build_tags` — id, name, `parent_id`, `depth`, and a `count` of board cards whose expanded ids include it, so a parent's count covers its descendants' cards. `BoardState.remember` keeps the parent map so `post_move` expands the returned card the same way. The page filters client-side with two **checkbox dropdowns**: Project lists the projects with a card on the board plus `Inbox`; Tag lists the whole tree indented by depth (zero-count tags muted but selectable) plus `Untagged`. Within a dropdown the picks are ORed, across the two they are ANDed, and no pick means show all; picking a parent tag matches cards tagged with any descendant because the ids are pre-expanded. The dropdown containers are never replaced by a render, so an open panel survives the 30-second auto-refresh. **Move** (`MOVE_TASK_JXA` / `move_task`) is the plug-in's exact operation, `task.removeTags(lanes); task.addTag(lane)`, followed by a re-read of that task's card. Before any osascript call, `validate_move` requires both ids to match `^[A-Za-z0-9_-]{1,64}$` **and** to be present in the id sets `BoardState` captured from the most recent successful read — so, as in the sorter, only identifiers OmniFocus itself returned reach the OmniJS source; the OmniJS side re-checks the lane is a `Kanban` child. `BoardState.lock` serializes every osascript call. `POST /api/move` also requires an `X-Kanban` header (a cross-origin page cannot add one without a CORS preflight the server never answers). The server uses `omnifocus_common.run_jxa_or_raise`, which raises `JxaError` instead of exiting, so an OmniFocus failure becomes a `500` the page shows in a banner while keeping the last good board; `run_jxa` is now a wrapper over it with unchanged CLI behaviour. Tests cover the pure helpers, `BoardApp` with injected read/move, and the HTTP layer via a real `ThreadingHTTPServer` on port 0; the page itself is verified manually.

When `X_BEARER_TOKEN` is set, `review_task` also appends any linked X post's text to the task content via `omnifocus_x` (a run-scoped `XPostFetcher` built in `review_tasks` dedupes by post id and caps lookups at `X_FETCH_MAX_USES`, default 25, reusing triage's env vars); the model's `web_fetch` tool stays enabled for non-X URLs, the fetched X text is model input only and never enters the OmniJS write source, and with no token the step is skipped. Because the reviewer's per-task threads share one `XPostFetcher`, `XPostFetcher.texts_for` holds a `threading.Lock` so its dedup-cache write and check-then-increment on the use cap stay atomic under concurrency.

## Runtime requirements

- macOS with OmniFocus 3/4 installed.
- First run prompts for Automation permissions (System Settings → Privacy & Security → Automation) for the terminal app — required for `osascript` to control OmniFocus.
- `omnifocus_inbox_triage.py` requires the `anthropic` and `python-dotenv` packages (installed via `uv sync`) and an Anthropic API key. Provide the key via a local `.env` (copy `.env.example`), an exported `ANTHROPIC_API_KEY`, or an active `ant auth login` profile.
